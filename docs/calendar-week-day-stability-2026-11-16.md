# 주간·일간 보기와 저장 반응 — 2026-11-16

## 이번에 확정한 화면

사용자가 이 대화에 표시된 시안 1과 3을 선택했다. 1은 두 주를 채우는 주간 보기, 3은 선택한 날짜의 일간 목록이다. 한 주에 일곱 긴 열을 쓰는 시안 2는 보류한다. 주간 버튼을 다시 누르면 일간으로, 다시 누르면 월간으로 돌아간다. 별도의 전체 화면이나 중첩 시트를 만들지 않는다.

- 주간은 일정과 미완료 Todo를 함께 끝까지 그린다. `+N`으로 남은 항목을 감추지 않는다. 날짜 행은 필요한 만큼 자라고 기존 캘린더의 한 스크롤 안에서 아래 내용까지 볼 수 있다. 월간의 기존 정보량 설정은 유지한다.
- 일간은 위쪽 일곱 날짜 중 선택한 하루의 시간·제목·출처를 표시한다. 일정 상세·수정·할 일 추가는 기존 경로를 쓴다. 시안 3에 여러 날이 보였지만 사용자의 최신 선택에 따라 한 날짜만 표시한다.
- Duo의 맨 위 장식 오리 마크와 그 헤더 높이를 제거한다. 카메라 열·반대 pane·오늘/보기 버튼·키보드 내리기 포털은 유지한다. 일반 iPhone의 상단과 하단 다섯 탭은 유지한다.
- Todo 탭을 다시 누르면 맨 위로 스크롤한다. 편집 중인 초안이나 드래그를 버리거나, 닫은 뒤 뒤늦게 이동하지 않는다. 동작 줄이기를 따른다.

## 저장을 누르면 먼저 보여준다

Todo 작성/내용 수정은 원래 편집창을 닫고 목록에 먼저 표시한다. 실제 서버 응답 전에는 ‘저장 중’이다. 확실한 4xx 거절에는 이전 값으로 돌아가고 덕 채팅에 이유·대안을 남긴다. 응답이 끊겼다는 사실만으로 실패나 미저장으로 판단하지 않는다.

새 Todo에는 계정에 묶인 요청 번호를 사용한다. 같은 번호가 다시 도착해도 같은 Todo를 반환하며, 응답 유실은 소유자 전용 읽기 API로 확인한다. 내용 수정의 응답 유실은 해당 항목을 다시 읽어 요청한 필드가 실제 저장됐는지 비교한다. 확인되지 않은 항목을 다시 수정/삭제하지 않으며 조회를 통해 확인할 수 있다. 계정·서버 변경 뒤 예전 결과를 현재 화면에 넣지 않는다.

캘린더는 기존 권한·원본 버전 확인과 저장 전 미리보기를 유지한다. 사용자가 실행을 확인하면 편집창을 닫고 변경을 먼저 표시한다. 서버의 실행 ID로 성공을 확인한 뒤 실제 저장본으로 바꾼다. 확정 실패는 표시 변경을 제거하고, 불확실하면 ‘저장 결과 확인 중’으로 남긴다. POST 확인을 반복하지 않고 같은 실행 결과를 읽는다. 덕 부가 정보는 기존 개정 번호의 멱등 저장을 사용한다.

캘린더의 임시 표시는 공유 메모리의 별도 계층이다. 마지막 원본 snapshot/ETag/쓰기 권한을 조작하거나 디스크에 가짜 저장본을 남기지 않는다. 두 pane과 Todo가 같은 변경을 보고, 느린 새로고침이 임시 변경을 덮지 않는다. 계정 전환/연결 해제 시 제거한다. 확정 전 Todo의 새 알림은 예약하지 않고, 수정 중인 기존 알림은 마지막 확정 내용을 유지한다.

이는 완전한 오프라인 앱이나 iOS 종료 후에도 클라이언트가 실행된다는 보장이 아니다. 서버에 아직 도착하지 않은 메모리상의 임시 변경은 앱 종료 후 보존을 보장하지 않는다. 서버에 접수·저장된 원본 동기화 대기열은 아래와 같이 재시작을 견딘다.

## 덕 저장과 원본 저장의 분리

Google에서 가져온 항목은 덕의 변경과 암호화된 원본 전송 작업을 같은 DB 트랜잭션으로 저장한다. HTTP 요청은 원본 네트워크 호출을 기다리지 않고 `queued`로 돌아온다. 아직 보내지 않은 변경은 합치고, 이미 실행 중이거나 결과가 불확실한 작업의 기록은 보존한다. 이전 결과가 새 편집을 덮지 않는다.

작업자는 실행 ID를 DB에 먼저 기록하고 기존 assistant의 권한·계정·이메일 인증·ETag 검사를 거쳐 확인한다. 작업자가 사라지면 5분 임대 후 같은 실행 결과를 읽는다. 이미 성공한 실행을 다시 보내지 않으며, 실행 중/unknown인 결과를 성공으로 추정하지 않는다. 미해결 unknown은 뒤 원본 쓰기도 막고 덕 채팅에 원본 확인과 대안을 알린다. 끝난 기록은 7일 후 정리하며 unknown은 보존한다. 백업 복원은 대기 작업을 중지한다.

Google Tasks의 완료/되돌리기와 지원되는 내용 편집을 다루고, Calendar에 없는 완료 기능을 삭제로 대체하지 않는다. Apple 미리알림은 기존 가져온 아이폰의 EventKit 쓰기·실제 완료 readback·현재 revision과 수정 시각 검사를 유지한다. 웹/서버가 아이폰 권한을 대신 행사하지 않는다. 직접 작성 항목은 외부 호출 없이 덕에서만 바꾼다.

구버전 설치 앱에는 새 `queued` 값을 기존에 읽을 수 있는 `unknown` 형태로 전달해 목록을 비우는 형식 오류를 막는다. 새 앱은 `writeStatus=2`로 대기 상태를 구분해 ‘원본 반영 중’을 표시하고, 대기 중에는 중복 재시도 버튼을 숨긴다. 원본 반영이 확인되면 Todo 조회가 캘린더 snapshot도 바로 갱신한다.

## DB 대기가 모든 요청을 막지 않게 한다

기존 libSQL HTTP 드라이버의 동기 호출이 Node의 유일한 HTTP 루프를 막았다. 기존 무료 Render 서비스 안에서 기본 저장/인증과 외부 연결/비서 작업을 두 worker thread로 나누고, 공개 HTTP/health 루프를 분리했다. 새 Render worker 서비스, 유료 서버, 디스크, Redis를 만들지 않았다. 실제 DB·암호화 키·세션·Origin/쿠키·IP 제한은 그대로이며 worker는 loopback에서만 듣는다. 내부 주소 헤더는 공개 프록시에서 지우고 내부 키로 검증한다.

동기 드라이버 자체를 비동기로 바꾼 것은 아니다. 같은 lane 안에서는 여전히 DB 지연이 생길 수 있고, 외부 공급자 장애나 무료 서비스의 기동 지연이 없어지는 것도 아니다. 긴 요청은 경로 분류·상태·전체 시간·DB 호출 수/시간·공급자 호출 수/시간을 기록한다. 원문 URL, SQL, 계정, 제목, 토큰은 로그에 남기지 않는다.

격리된 실제 libSQL HTTP fixture에 요청당 100ms 지연을 주고 외부 연결 lane에서 8개 동기 쿼리를 실행했다. 그동안 health는 8ms, 별도 기본 저장은 223ms에 응답했다. 이는 운영 지연 실측이 아니다. 기존 격리 실험의 단일 루프에서는 동일 유형의 8개 조회가 약 1.6초 동안 타이머도 막았다.

## 채팅 전송

사용자가 확인한 증상은 ‘글자는 써지지만 전송 버튼이 작동하지 않음’이다. 전송을 막는 조건을 조용한 disabled 화살표에만 두지 않고, 눌렀을 때 연결·동의·사용 예산의 구체적인 이유와 다시 확인을 표시한다. 글은 유지하고, 조건이 갖춰지지 않은 모델 호출은 하지 않는다. 프로 권한과 실제 사용 예산/공급자 잔액을 분리하며 가짜 정산이나 예산을 넣지 않았다. 예산이 준비된 합성 응답에서는 동의 후 한 번 전송하는 것까지 검증했다. 실제 운영 AI 정상 응답이나 API 계정의 충전을 확인한 것은 아니다.
